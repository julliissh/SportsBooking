Лабораторна робота №3 — Повний гайд до захисту

Предметна область: SportsBooking (Бронювання спортивних майданчиків)
Склад системи: API Gateway (порт 5000) + Auth + Catalog + Booking у Docker Compose

Суть роботи: Ми перетворили шлюз ApiGateway (порт 5000) із простого маршрутизатора, зробленого в ЛР1–2, на єдині захищені вхідні двері системи без бізнес-логіки: додали складений ендпоінт екрана деталей майданчика (паралельний виклик CatalogService + BookingService через Task.WhenAll), задали таймаути 2 с зі свідомою обробкою збоїв (часткова відповідь "unavailable" або 503 ProblemDetails), перенесли перевірку JWT-токена на шлюз із примусовим видаленням підроблених X-User-Id, закрили зовнішні порти сервісів у Docker (expose), підключили кеш IMemoryCache (TTL 30 с) для спільних даних каталогу з миттєвою інвалідизацією при змінах, налаштували Rate Limiting (429 + Retry-After) і довели роботу 18 інтеграційними тестами.
🗣️ 30 секунд, щоб відкрити розмову з викладачем (прочитай на початку захисту):
«Шлюз на 5000 — єдині вхідні двері. Складений запит паралельно бере майданчик із Catalog і мою активну бронь із Booking. Таймаут — 2 с. Якщо Booking не відповів, шлюз віддає 200 і статус unavailable, а якщо Catalog — то 503. Токен перевіряється на шлюзі, клієнтські заголовки X-User-Id примусово стираються. Порти внутрішніх сервісів у Docker закриті через expose. Кеш увімкнено лише для каталогу, ключ без користувача, TTL 30 с, скидається миттєво після PUT/POST/DELETE. Ліміти: логін — 10/хв за IP, бронь — 10/хв за юзером, загальний — 100/хв, анонім — 30/хв. Тести: 18 зелених».

Розділ 2. Розбір коду ЛР3: де змінили, на що, як працює і навіщо

1. Складений ендпоінт і паралельний виклик (Task.WhenAll)
Де лежить: src/ApiGateway/Controllers/VenueDetailsController.cs (рядки 123–168)
Що змінили порівняно з ЛР2: У ЛР2 шлюз вміє лише тупо пересилати запити через Ocelot. Ми додали власний контролер шлюзу, який сам паралельно звертається до двох сервісів і склеює екран для клієнта. 
// 1. Запускаємо обидва виклики ОДНОЧАСНО (не чекаємо завершення першого перед стартом другого!)
var venueTask = _catalogClient.GetVenueAsync(venueId, correlationId, ct);
var bookingTask = _bookingClient.GetMyActiveAsync(venueId, userId, bearerToken, correlationId, ct);

await Task.WhenAll(venueTask, bookingTask); // Чекаємо, поки обидва завершаться паралельно

var venueResult = venueTask.Result;
var bookingResult = bookingTask.Result;

// 2. Якщо майданчика з таким ID взагалі немає в каталозі -> повертаємо 404 ProblemDetails
if (venueResult.Status == GwStatus.NotFound)
    return NotFound(new ProblemDetails { Status = 404, Title = "Venue not found", Detail = $"Venue {venueId} not found." });

// 3. ПОВНА ВІДМОВА: якщо впав головний сервіс (CatalogService) -> повертаємо 503 ProblemDetails на весь запит
if (venueResult.Status == GwStatus.Unavailable)
    return StatusCode(503, new ProblemDetails { Status = 503, Title = "Catalog service unavailable" });

// 4. ЧАСТКОВА ВІДПОВІДЬ: якщо впав другорядний сервіс (BookingService) -> віддаємо майданчик, але явно пишемо "unavailable"
var bookingStatus = bookingResult.Status switch {
    GwStatus.Ok          => "active",      // Активна бронь знайдена
    GwStatus.NotFound    => "none",        // Сервіс відповів, що активної броні у юзера немає (204 NoContent)
    GwStatus.Unavailable => "unavailable", // Сервіс бронювань лежить або перевищив таймаут 2 с!
    _ => "none"
};

return Ok(new VenueDetailsAggDto(Venue: venueResult.Data!, MyActiveBooking: bookingResult.Data, BookingStatus: bookingStatus));
Пояснення простими словами (навіщо і як працює):
  • Навіщо Task.WhenAll: Обидва запити летять по мережі одночасно. Якщо Catalog відповідає за 150 мс, а Booking за 200 мс, то клієнт чекатиме лише 200 мс (за найдовшим), а не 350 мс (якби викликали по черзі через два окремі await).
  • Навіщо поле bookingStatus: Викладач вимагає, щоб клієнт відрізняв «даних немає» ("none") від «сервіс впав» ("unavailable"). Якби ми мовчки повертали null, клієнт подумав би, що його бронювання не існує, і створив би друге таке саме!
2. Таймаути (2 с) та клієнти шлюзу
Де лежить: src/ApiGateway/Program.cs (рядки 205–221) та src/ApiGateway/Clients/CatalogGwClient.cs (рядки 45–88)
Що змінили порівняно з ЛР2: Додали жорсткий дедлайн 2 секунди на всі вихідні HttpClient шлюзу та в ocelot.json ("TimeoutValue": 2000). 
// У Program.cs реєструємо типізовані клієнти з таймаутом 2 секунди:
builder.Services.AddHttpClient<ICatalogGwClient, CatalogGwClient>(client => {
    client.BaseAddress = new Uri(catalogUrl);
    client.Timeout = TimeSpan.FromSeconds(2); // Якщо сервіс думає довше 2 с — виклик примусово обірветься!
});

// У CatalogGwClient.cs (і так само в BookingGwClient.cs) ловимо обрив за таймаутом або помилку мережі:
try {
    using var response = await _http.SendAsync(request, ct);
    if (response.StatusCode == HttpStatusCode.NotFound) return new GwResult<VenueDto>(GwStatus.NotFound);
    if (!response.IsSuccessStatusCode) return new GwResult<VenueDto>(GwStatus.Unavailable);
    ...
}
catch (Exception ex) when (ex is HttpRequestException or TaskCanceledException or TimeoutException) {
    _logger.LogError(ex, "CatalogService unavailable for venue {VenueId}", venueId);
    return new GwResult<VenueDto>(GwStatus.Unavailable); // Не валимо шлюз, а повертаємо статус Unavailable!
}
Пояснення простими словами: Коли один із сервісів зависає довше ніж на 2 секунди, HttpClient викидає TaskCanceledException. Наш блок catch ловить її і спокійно повертає статус GwStatus.Unavailable. Завдяки цьому потоки шлюзу не блокуються назавжди і шлюз ніколи не падає разом із завислим сервісом.
3. Перевірка JWT-токена на шлюзі та захист від підробки X-User-Id
Де лежить: src/ApiGateway/Program.cs (рядки 88–123 та 303–326) + docker-compose.yml
Що змінили порівняно з ЛР2: У ЛР2 шлюз не перевіряв токен сам. Тепер шлюз валідує JWT на вході, видаляє підроблені клієнтом заголовки X-User-Id і записує туди справжній ID із токена. А в docker-compose.yml порти сервісів закрили через expose. 
app.UseAuthentication(); // 1. Шлюз перевіряє підпис, термін дії та видавця JWT-токена

app.Use(async (context, next) =>
{
    // 2. ЗАХИСТ: Примусово стираємо заголовки X-User-Id та X-User-Roles, які міг підсунути хитрий клієнт!
    context.Request.Headers.Remove("X-User-Id");
    context.Request.Headers.Remove("X-User-Roles");

    // 3. Якщо користувач пройшов перевірку токена — витягуємо його справжній ID з клейма "sub"
    if (context.User.Identity?.IsAuthenticated == true)
    {
        var uid = context.User.FindFirstValue("sub") ?? context.User.FindFirstValue(ClaimTypes.NameIdentifier);
        if (!string.IsNullOrWhiteSpace(uid))
            context.Request.Headers["X-User-Id"] = uid; // Передаємо вниз перевірений ID!
    }
    await next();
});
Пояснення простими словами: Чому це критично важливо? Якби ми не робили Headers.Remove("X-User-Id"), будь-хто ззовні міг би надіслати запит із заголовком X-User-Id: 1 і вкрасти дані адміністратора. А оскільки ми стираємо клієнтський заголовок і закрили порти сервісів (expose: 5001, 5002, 5003 у Docker), ніхто не може обійти шлюз напряму.
4. Локальний кеш каталогу (IMemoryCache) та миттєва інвалідизація при змінах
Де лежить: src/ApiGateway/Middleware/CatalogCacheMiddleware.cs та src/ApiGateway/Services/CatalogCacheService.cs
Що додали в ЛР3: Кешування спільних даних каталогу на 30 секунд і скидання кешу після POST/PUT/DELETE. 
public async Task InvokeAsync(HttpContext context)
{
    // 1. ПРАВИЛО БЕЗПЕКИ: Кешуємо ТІЛЬКИ спільний каталог (/api/v1/catalog). Персональні маршрути проходять повз!
    if (!context.Request.Path.StartsWithSegments("/api/v1/catalog")) {
        await _next(context);
        return;
    }

    // 2. ІНВАЛІДИЗАЦІЯ: Якщо адмін змінює каталог (POST, PUT, DELETE) і сервіс відповів успіхом (200..299)
    var method = context.Request.Method;
    if (HttpMethods.IsPost(method) || HttpMethods.IsPut(method) || HttpMethods.IsDelete(method)) {
        await _next(context);
        if (context.Response.StatusCode >= 200 && context.Response.StatusCode < 300)
            _cacheService.Invalidate(); // Миттєво скидає весь кеш каталогу через CancellationTokenSource.Cancel()!
        return;
    }

    // 3. Будуємо ключ кешу БЕЗ користувача: "GET:/api/v1/catalog/items?category=Football&page=1"
    var cacheKey = BuildCacheKey(context.Request);
    if (_cache.TryGetValue(cacheKey, out CachedHttpResponse? cached) && cached is not null) {
        _cacheService.RecordHit();
        context.Response.Headers["X-Cache"] = "HIT"; // Віддаємо миттєво з RAM шлюзу без виклику сервісу!
        await context.Response.Body.WriteAsync(cached.Body);
        return;
    }

    // 4. Якщо в кеші немає (MISS) — викликаємо сервіс і кладемо відповідь у кеш на 30 секунд (TTL)
    _cacheService.RecordMiss();
    ...
    var entryOptions = new MemoryCacheEntryOptions()
        .SetAbsoluteExpiration(TimeSpan.FromSeconds(30))          // TTL = 30 секунд
        .AddExpirationToken(_cacheService.GetExpirationToken());  // Прив'язка до токена скидання!
    _cache.Set(cacheKey, toCache, entryOptions);
    context.Response.Headers["X-Cache"] = "MISS";
}
Пояснення простими словами:
  • Що кешуємо: Тільки /api/v1/catalog, бо список спортивних майданчиків однаковий для всіх людей. Мої бронювання (/api/bookings) і мій профіль (/api/v1/users) не кешуються взагалі, щоб один користувач ніколи не побачив чужу бронь!
  • Як працює інвалідизація: Всі записи в кеші прив'язані до одного «стоп-крана» (CancellationChangeToken у CatalogCacheService). Коли адмін змінює ціну майданчика через PUT, шлюз смикає метод Invalidate(), який натискає цей стоп-кран — і всі старі записи миттєво зникають із пам'яті, не чекаючи 30 секунд!
5. Обмеження частоти запитів (Rate Limiting) — захист від спаму і підбору паролів
Де лежить: src/ApiGateway/Program.cs (рядки 127–199)
Що додали в ЛР3: Вбудований Microsoft.AspNetCore.RateLimiting з розділенням лімітів та відповіддю 429. 
builder.Services.AddRateLimiter(options =>
{
    options.RejectionStatusCode = StatusCodes.Status429TooManyRequests;
    options.GlobalLimiter = PartitionedRateLimiter.Create<HttpContext, string>(ctx =>
    {
        var ip = ctx.Connection.RemoteIpAddress?.ToString() ?? "anon";
        var uid = ctx.User.FindFirstValue("sub"); // ID авторизованого користувача з токена

        // 1. Вхід у систему (POST /api/v1/auth/login) — жорсткий ліміт 10 спроб/хв за IP (захист від підбору паролів)
        if (HttpMethods.IsPost(ctx.Request.Method) && path.StartsWithSegments("/api/v1/auth/login"))
            return RateLimitPartition.GetFixedWindowLimiter($"login:{ip}", _ => FixedOpt(10));

        // 2. Створення бронювань (POST /api/bookings) — 10 запитів/хв за ID юзера
        if (HttpMethods.IsPost(ctx.Request.Method) && path.StartsWithSegments("/api/bookings"))
            return RateLimitPartition.GetFixedWindowLimiter($"book:user:{uid ?? ip}", _ => FixedOpt(10));

        // 3. Авторизований юзер — 100 запитів/хв за його UserId; Анонім — 30 запитів/хв за IP
        return uid is not null
            ? RateLimitPartition.GetFixedWindowLimiter($"general:user:{uid}", _ => FixedOpt(100))
            : RateLimitPartition.GetFixedWindowLimiter($"general:ip:{ip}", _ => FixedOpt(30));
    });

    // Коли ліміт перевищено — беремо з лічильника скільки секунд лишилось до кінця вікна (або запасне 60)
    options.OnRejected = async (ctx, ct) => {
        ctx.HttpContext.Response.Headers.RetryAfter =
            ctx.Lease.TryGetMetadata(MetadataName.RetryAfter, out var retryAfter)
                ? ((int)retryAfter.TotalSeconds).ToString() : "60";
        await ctx.HttpContext.Response.WriteAsJsonAsync(new ProblemDetails {
            Status = 429, Title = "Too Many Requests", Detail = "Rate limit exceeded. Please retry later."
        }, ct);
    };
});
Пояснення простими словами: Чому авторизованих рахуємо за uid (general:user:5), а анонімів за ip (general:ip:192.168.1.1)? Тому що в офісі чи університеті за однією IP-адресою Wi-Fi сидить сотня студентів. Якщо рахувати авторизованих за IP, один спамер заблокує роботу всім іншим. А коли кожен має свій ліміт за userId, страждає лише сам порушник. Заголовок Retry-After показує, скільки секунд залишилося до кінця поточного хвилинного вікна (наприклад, 37).

Розділ 5. Готові відповіді на ВСІ 11 контрольних питань + 3 каверзні питання

1. Що таке API Gateway і за що він відповідає?
Відповідь: Це єдині вхідні двері системи для зовнішніх клієнтів (порт 5000). Він відповідає за маршрутизацію запитів до мікросервісів, одноразову перевірку JWT-токена, обмеження частоти запитів (Rate Limiting), кешування спільних публічних даних, встановлення таймаутів та збирання одного екрана з кількох сервісів (складений запит).
2. Чому в шлюзі не має бути бізнес-логіки? Наведіть приклад правила, яке туди просилося, але не належить.
Відповідь: Якщо перенести у шлюз бізнес-правила та розрахунки, він перетвориться на другий моноліт, через який іде весь трафік. Приклад правила: «Якщо бронювання триває більше 3 годин — дати знижку 15%» або «Перевірити, чи не перетинається час броні з іншими». Це правило належить суто BookingService, який володіє даними бронювань.
3. Чому виклики у складеному ендпоінті виконують паралельно? Як зміниться час відповіді, якщо зробити їх послідовно?
Відповідь: При паралельному виклику через Task.WhenAll запити до Catalog і Booking виконуються одночасно, тому загальний час дорівнює найдовшому виклику: max(T1, T2) (наприклад, max(200 мс, 250 мс) = 250 мс). Якщо зробити їх послідовно, час складеться: 200 + 250 = 450 мс, і клієнт чекатиме майже вдвічі довше.
4. Що станеться зі шлюзом, якщо прибрати таймаути, а один із сервісів зависне?
Відповідь: Один завислий сервіс «покладе» весь шлюз і всю систему (каскадна відмова). Запити в шлюзі накопичуватимуться, усі потоки пулу займуться нескінченним очікуванням, пам'ять вичерпається, і шлюз перестане відповідати навіть на ті маршрути, чиї сервіси працюють нормально.
5. Чому клієнт має відрізняти «даних немає» від «сервіс недоступний»?
Відповідь: Якщо BookingService впав, а шлюз мовчки поверне myActiveBooking: null (так само, як коли бронювань немає), користувач подумає, що його бронювання не створилося, і натисне кнопку «Забронювати» вдруге — створить дублікат і двічі спише кошти. Тому ми явно повертаємо bookingStatus: "unavailable".
6. Чому перевірку токена винесли на шлюз? За якої умови сервіс може довіряти заголовку X-User-Id?
Відповідь: Щоб перевіряти токен один раз на вході й одразу відсікати неавторизовані запити (401) без навантаження на внутрішні сервіси. Сервіс може довіряти заголовку X-User-Id лише за двох умов: 1) до сервісу неможливо достукатися напряму ззовні в обхід шлюзу (закриті порти expose); 2) шлюз завжди видаляє заголовок X-User-Id, надісланий клієнтом, і записує туди ID сам із перевіреного токена.
7. Які дані ви кешуєте і чому саме їх? Чому персональні дані не кешують?
Відповідь: Ми кешуємо тільки спільні публічні дані — каталог майданчиків (GET /api/v1/catalog/**), бо вони однакові для всіх користувачів і читаються набагато частіше, ніж змінюються. Персональні дані (мої бронювання, мій профіль) кешувати не можна: це критична вразливість безпеки, через яку один користувач може отримати з кешу чужі персональні дані.
8. З чого складається ваш ключ кешу? Як ви обирали TTL?
Відповідь: Ключ складається з HTTP-методу, шляху маршруту та відсортованих параметрів запиту (пагінації, категорії): GET:/api/v1/catalog/items?category=Football&page=1. Для об'єкта у клієнті: venue:{venueId}. Користувача в ключі немає. TTL = 30 секунд — баланс між розвантаженням бази даних при сплесках трафіку та свіжістю даних.
9. Навіщо потрібна інвалідизація, якщо є TTL?
Відповідь: Поки не спливе TTL (30 секунд), клієнти бачили б у каталозі стару ціну майданчика навіть після того, як адміністратор її змінив. Інвалідизація примусово очищує кеш одразу після успішного POST/PUT/DELETE через шлюз, тому клієнти бачать оновлену ціну миттєво.
10. Чим fixed window відрізняється від token bucket? Що ви обрали і чому?
Відповідь: Fixed window рахує не більше N запитів за фіксований відрізок часу (наприклад, 10 за хвилину), але на межі хвилин може пропустити подвійний сплеск. Token bucket має «відро жетонів», яке поповнюється з постійною швидкістю і дозволяє короткі сплески трафіку. Ми обрали FixedWindowLimiter з розділенням квот (10/хв на логін, 10/хв на бронь, 100/хв загальний), бо він простий, передбачуваний і надійно блокує підбір паролів.
11. Чому ліміт для анонімних запитів рахують за IP, а для авторизованих — за користувачем?
Відповідь: Про анонімного клієнта шлюз знає лише його IP-адресу. А для авторизованих ліміт рахують за userId з токена, бо за одним публічним IP (офісний NAT, університетський Wi-Fi, мобільний оператор) можуть одночасно працювати десятки чесних користувачів. Якби їх рахували за IP, один активний юзер вичерпав би ліміт і заблокував усіх інших.
⚠️ Каверзне питання 1: «Токен перевіряється один раз на шлюзі, а в тебе і сервіси його перевіряють?»
Відповідь: Так. Шлюз перевіряє токен на вході і передає вниз сам токен та заголовок X-User-Id. А сервіси ще раз перевіряють підпис токена, бо мають свій Jwt__Key, і беруть userId із токена. Це захист у два шари (Defense in Depth): заголовок X-User-Id шлюз очищує й передає, але сервіси додатково довіряють саме токену, тож навіть якби порт випадково відкрили, підробити користувача не вийде.
⚠️ Каверзне питання 2: «Ти кажеш, що шлюз без бізнес-логіки, а bookingStatus: "active"/"none"/"unavailable" — це не логіка?»
Відповідь: Ні, це не бізнес-логіка. Це лише технічна позначка стану мережевої відповіді для екрана клієнта (є дані / немає даних / сервіс не відповів). Шлюз не вирішує, чи можна бронювати майданчик, не перевіряє перетин часу і не рахує суми чи знижки — усі ціни та бізнес-правила тримає BookingService.
⚠️ Каверзне питання 3: «У Docker є monolith? Бо в ocelot.json є маршрут на порт 5100».
Відповідь: Ні, у docker-compose.yml моноліту немає. Моноліт залишено в репозиторії з попередніх лабораторних для порівняння, він запускається окремо через dotnet run на порту 5100. У ЛР3 в Docker працюють шлюз та 3 мікросервіси: Auth, Catalog і Booking.
