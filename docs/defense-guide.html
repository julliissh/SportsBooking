Лабораторна робота №2 — Повний гайд до захисту

Предметна область: SportsBooking (Бронювання спортивних майданчиків)
Оцінка: 10 / 10 обов'язкових балів + +3 бали за Docker Compose = 13 балів

Суть роботи: Ми винесли операційний модуль бронювань із моноліту в окремий незалежний мікросервіс BookingService (порт 5003, окрема БД miniproject_booking), прибрали зовнішні ключі між базами, додали перевірку каталогу з таймаутом 2 с, захистили створення ідемпотентністю (Idempotency-Key), зберегли знімок цін (ItemSnapshot), перемкнули шлюз ApiGateway (:5000) і довели 10 інтеграційними тестами (dotnet test), що система працює без регресій.

Розділ 2. Що конкретно вводити в Swagger (Покроковий приклад)

Відкрийте в браузері: http://localhost:5003/swagger

Крок А. Авторизація в Swagger (отримати і вставити токен)

Оскільки всі операції захищені атрибутом [Authorize], спочатку треба авторизуватися:

  1. Отримайте токен прямо у Swagger AuthService:
    1. Відкрийте у сусідній вкладці браузера: http://localhost:5001/swagger
    2. Розкрийте блок POST /api/v1/auth/login і натисніть кнопку Try it out.
    3. У віконце Request body вставте логін і пароль: 
      {
  "email": "admin@sportsbooking.com",
  "password": "Admin123!"
}
    4. Натисніть кнопку Execute. Нижче у блоці Response body виділіть і скопіюйте довгий текст accessToken (без лапок).
  2. У Swagger BookingService (:5003/swagger) вгорі праворуч натисніть зелену кнопку Authorize 🔓.
  3. У полі Value вставте ваш токен: 
    Bearer ВСТАВИТИ_ВАШ_ТОКЕН_СЮДИ
    (або просто сам токен без слова Bearer) і натисніть кнопку Authorize, а потім Close. Замок закриється 🔒.
Крок Б. Створення нового бронювання (POST /api/bookings)
  1. Розкрийте зелений блок POST /api/bookings.
  2. Натисніть кнопку Try it out праворуч.
  3. У полі Request body вставте такий готовий JSON: 
    {
  "venueId": 1,
  "startTime": "2027-05-10T14:00:00Z",
  "hours": 2
}
  4. (Опціонально) У полі заголовка Idempotency-Key можна написати demo-key-1.
  5. Натисніть велику синю кнопку Execute.
  6. Результат: статус 201 Created, у відповіді повернеться бронювання з id (наприклад, 100), збереженим знімком майданчика "venueName": "Central Football Field" та порахованою сумою "totalPrice": 1000.00.
Крок В. Перегляд списку своїх бронювань (GET /api/bookings)
  1. Розкрийте синій блок GET /api/bookings.
  2. Натисніть Try it out.
  3. Параметри можна залишити за замовчуванням (page: 1, pageSize: 20, або ввести status: Confirmed).
  4. Натисніть Execute.
  5. Результат: статус 200 OK і JSON зі списком ваших бронювань та пагінацією.
Крок Г. Скасування бронювання (POST /api/bookings/{id}/cancel)
  1. Розкрийте блок POST /api/bookings/{id}/cancel.
  2. Натисніть Try it out.
  3. Введіть id вашого щойно створеного бронювання (наприклад, 100).
  4. Натисніть Execute.
  5. Результат: статус 200 OK, статус бронювання змінився на "status": "Cancelled".
  6. Якщо натиснути Execute ще раз — повернеться помилка 400 Bad Request («Бронювання вже скасовано»).

Дія 2. Підняти систему і показати власну БД з перенесеними даними
  • Покажіть запущений Docker Desktop (група sportsbooking горить зеленим) або виконайте: 
    docker compose up -d
  • Покажіть таблицю в MySQL (через Workbench або команду в консолі):

Розділ 4. Готові відповіді на ВСІ 11 контрольних питань (Розділ 14)

1. Що таке шов (seam) і за якими ознаками ви його шукали у своєму моноліті?
Відповідь: Шов — це межа в моноліті, де його можна розрізати без зміни коду інших частин. Ми поділили сутності моноліту на три групи: наші дані (Bookings — перенесли у власну БД), чужі дані (Venues, Users — читаємо по мережі або з JWT) та спільні дрібниці (статуси — здублювали локально в сервісі).
2. Чому між базами різних сервісів не роблять зовнішніх ключів? Що використовують замість них?
Відповідь: Мікросервіси мають бути автономними (принцип Database per Service), їхні БД можуть бути на різних серверах. Зовнішній ключ (FK) на рівні СУБД створив би жорстку залежність. Замість нього зберігають числове поле VenueId, перевіряють його по мережі через CatalogClient і фіксують знімок назви та ціни (ItemSnapshot).
3. Що таке характеризаційний тест і чим він відрізняється від звичайного?
Відповідь: Звичайний тест перевіряє код за вимогами («як має бути»). Характеризаційний тест (baseline) знімає фактичну поведінку існуючої системи («як вона відповідає сьогодні»), щоб після винесення переконатися, що жодна деталь і жоден код помилки не змінилися.
4. Чим інтеграційний тест відрізняється від модульного і від e2e-тесту?
Відповідь: Unit-тест перевіряє один клас в ізоляції без бази. Інтеграційний тест перевіряє конвеєр ASP.NET Core + валідацію + EF Core + тестову базу в пам'яті тестового процесу. E2E-тест перевіряє всю систему наскрізно через шлюз з реальними процесами.
5. Для чого потрібен WebApplicationFactory і що саме ви в ньому підмінили?
Відповідь: Він піднімає веб-застосунок у тестовому процесі без відкриття сокетів і без dotnet run. Ми підмінили в ньому: 1) робочу БД на окрему тестову miniproject_booking_test; 2) клієнта каталогу на стаб FakeCatalogClient із готовими відповідями.
6. Що таке ідемпотентність? Наведіть ідемпотентний і неідемпотентний метод.
Відповідь: Це властивість операції давати той самий результат при повторних викликах. Ідемпотентні за специфікацією: GET, PUT, DELETE. Неідемпотентний: POST. Щоб зробити наш POST ідемпотентним, ми додали заголовок Idempotency-Key та унікальний індекс у БД.
7. Навіщо виклику до сусіднього сервісу потрібен дедлайн? Що станеться без нього, якщо сусід «завис»?
Відповідь: Дедлайн (таймаут 2 с) обмежує час очікування. Без нього потік сервера чекатиме вічно, закінчаться вільні потоки пулу і наш сервіс теж впаде (каскадна відмова). Завдяки дедлайну ми повертаємо клієнту контрольований 503 код.
8. Чому в операції зберігають копію назви та ціни об’єкта каталогу, а не лише його Id?
Відповідь: Це патерн ItemSnapshot. Якщо через півроку в каталозі піднімуть ціну майданчика, старі бронювання клієнтів не повинні перераховуватися за новими тарифами. Знімок гарантує незмінність фінансової історії.
9. Як ви перенесли старі дані й чому підняли автоінкремент?
Відповідь: Записи зі старої бази (Id 1, 3, 4) внесені в міграцію InitialCreate через HasData. Командою ALTER TABLE Bookings AUTO_INCREMENT = 100 ми підняли стартовий номер, щоб нові Id починалися зі 100 і не перетиналися зі старими.
10. Що таке Strangler Fig і на якому його кроці ви зараз перебуваєте?
Відповідь: Це патерн поступової заміни моноліту мікросервісами через API Gateway. Ми перебуваємо на кроці, коли сервіси (Auth, Catalog, Booking) винесені, шлюз перемкнено на них, а старий моноліт залишено поруч як страховку на час перевірки.
11. Як ви дізналися б, що винесення зламало поведінку, якби не було baseline-файлів?
Відповідь: Без baseline це помітили б лише реальні клієнти після релізу (зміна регістру JSON, зниклий 404 код, зламана валідація). Базовий знімок дозволяє автоматично виявити регресії ще під час розробки.
