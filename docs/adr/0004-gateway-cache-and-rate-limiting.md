# ADR 0004: Кешування публічних відповідей каталогу та Rate Limiting на API Gateway

## Статус
Прийнято (ЛР3)

## Контекст
У ході розширення функціоналу API Gateway (ЛР3) виникли вимоги:
1. Захистити внутрішні сервіси від сплесків трафіку, DoS-атак та підбору паролів (brute-force).
2. Прискорити відповіді для публічного каталогу майданчиків (`GET /api/v1/catalog/**`) та зменшити навантаження на CatalogService і базу даних MySQL.
3. Категорично уникнути кешування конфіденційних / персональних даних користувачів.
4. Забезпечити коректну інвалідацію кешу при додаванні чи редагуванні об'єктів каталогу.

## Рішення

### 1. Стратегія кешування (CatalogCacheMiddleware)
- **Область застосування:** Виключно маршрути `GET /api/v1/catalog/**`. Складені запити, операції бронювання та аутентифікації **не кешуються**, оскільки містять персональні дані користувача.
- **Формування ключа кешу (Cache Key):**
  `GET:{path}?{sortedQuery}`
  Параметри рядка запиту обов'язково сортуються в алфавітному порядку (`orderby`). Це гарантує, що запити на зразок `?page=1&pageSize=10` та `?pageSize=10&page=1` звертаються до одного й того самого елемента кешу.
- **Час життя кешу (TTL):** 30 секунд (конфігурується у `appsettings.json: Cache:CatalogTtlSeconds`).
  *Обґрунтування TTL 30 с (Контрольне питання 8):* Каталог майданчиків є відносно статичним (зміни розкладу чи цін вносяться рідко), проте користувачі повинні бачити актуальні дані без значної затримки. 30 секунд — це баланс між захистом CatalogService від "read-heavy" навантаження та швидкістю оновлення інформації для клієнта.
- **Механізм інвалідації:** Використовується `CancellationTokenSource` та `CancellationChangeToken`. Усі записи кешу каталогу (включаючи `IMemoryCache` у `CatalogGwClient` та `CatalogCacheMiddleware`) прив'язані до токена. При успішному виконанні будь-якої мутуючої операції (`POST`, `PUT`, `DELETE`, `PATCH` на `/api/v1/catalog/**` зі статусом 2xx), токен скасовується через `Interlocked.Exchange`, що миттєво інвалідує всі закешовані відповіді без перебору ключів.
- **Заголовки:** Шлюз повертає заголовок `X-Cache: HIT` (якщо відповідь віддано з кешу) або `X-Cache: MISS` (якщо запит пройшов до сервісу).
- **Метрики:** Ендпоінт `GET /health/cache-stats` повертає поточну кількість `hits` та `misses`, які обліковуються потокобезпечно через `Interlocked`.

### 2. Стратегія обмеження частоти запитів (Rate Limiting)
- Використано вбудований у .NET 9 `Microsoft.AspNetCore.RateLimiting` з єдиним `GlobalLimiter`.
- **Обґрунтування алгоритму Fixed Window:** Обрано алгоритм Fixed Window з вікном у 1 хвилину замість Sliding Window або Token Bucket з таких причин:
  1. *Простота та швидкість:* Мінімальні накладні витрати на пам'ять ($O(1)$ стан на ключ) без потреби зберігати історію часових міток кожного запиту.
  2. *Нативна оптимізація:* Використовує високопродуктивну реалізацію з `System.Threading.RateLimiting`, оптимізовану під високе навантаження ASP.NET Core.
  3. *Прозорість для клієнта:* Заголовок `Retry-After` чітко вказує секунди до початку наступного фіксованого вікна.
- **Правила розподілу лімітів:**
  1. `/health` та `/health/cache-stats` — без обмежень (`GetNoLimiter`).
  2. `POST /api/v1/auth/login` — 10 запитів/хв за IP-адресою клієнта (захист від перебору паролів).
  3. `POST /api/bookings` — 10 запитів/хв за `userId` (з клейма `sub` перевіреного токена), або за IP для анонімних звернень.
  4. Загальні запити — роздільні ліміти: **100 запитів/хв** за `userId` для автентифікованих користувачів та більш суворий ліміт **30 запитів/хв** за IP для анонімних клієнтів.
- **Поведінка при перевищенні:** Статус `429 Too Many Requests` у форматі `ProblemDetails` з динамічним заголовком `Retry-After`.

## Наслідки
- Всі публічні запити каталогу обслуговуються з пам'яті шлюзу за частки мілісекунди при повторних викликах.
- Запобігання DoS та brute-force атакам.
- Конфіденційні дані користувачів не потрапляють у кеш.
