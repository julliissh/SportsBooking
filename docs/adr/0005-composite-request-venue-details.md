# ADR 0005: Реалізація складеного запиту для екрана деталей майданчика

## Статус
Прийнято (ЛР3)

## Контекст
Для відображення сторінки спортивного майданчика клієнтському додатку (Web / Mobile) одночасно потрібні:
1. Загальні дані майданчика (назва, адреса, ціна за годину, категорія) із `CatalogService`.
2. Інформація про те, чи має поточний авторизований користувач активне підтверджене бронювання цього майданчика із `BookingService`.

Робити два окремих запити з клієнта неефективно (підвищена затримка мережі на мобільних пристроях). Робити послідовні запити на шлюзі неприпустимо за вимогами продуктивності (методичні рекомендації вимагають виключно паралельних викликів через `Task.WhenAll`).

## Рішення

### 1. Ендпоінт та архітектура
Створено контролер `VenueDetailsController` безпосередньо в `ApiGateway`:
`GET /api/gateway/venues/{venueId}/details`
Маршрут захищений атрибутом `[Authorize]`.

### 2. Паралельне виконання (Task.WhenAll)
Оскільки `venueId` відомий одразу з URL маршруту, обидва downstream-виклики ініціюються одночасно:
```csharp
var venueTask = _catalogClient.GetVenueAsync(venueId, correlationId, ct);
var bookingTask = _bookingClient.GetMyActiveAsync(venueId, userId, bearerToken, correlationId, ct);

await Task.WhenAll(venueTask, bookingTask);
```

### 3. Таймаути та обробка збоїв (Fault Tolerance & Graceful Degradation)
- Обидва `HttpClient` налаштовані з таймаутом `Timeout = TimeSpan.FromSeconds(2)`.
- Клієнти не викидають необроблених винятків, а загортають відповідь у типізований результат `GwResult<T>` зі статусами `Ok`, `NotFound`, `Unavailable`.
- **Логіка формування відповіді:**
  1. Якщо **CatalogService** повертає `NotFound` → шлюз віддає `404 Not Found` (ProblemDetails).
  2. Якщо **CatalogService** недоступний або стався таймаут → шлюз віддає `503 Service Unavailable` (ProblemDetails), оскільки майданчик є базовим об'єктом екрана.
  3. Якщо **BookingService** недоступний, але каталог доступний → шлюз віддає `200 OK` із заповненим об'єктом `venue`, `myActiveBooking = null` та явним статусом `bookingStatus: "unavailable"`.
     *Це дозволяє клієнту відобразити інформацію про майданчик і показати попередження про тимчасову недоступність перегляду бронювань.*
  4. Якщо активного бронювання немає → `200 OK`, `bookingStatus: "none"`, `myActiveBooking = null`.
  5. Якщо активне бронювання є → `200 OK`, `bookingStatus: "active"`, `myActiveBooking` містить деталі бронювання.

### 4. Безпека та передача контексту
- Шлюз валідує JWT перед викликом контролера.
- Будь-які заголовки `X-User-Id` та `X-User-Roles`, надіслані клієнтом ззовні, примусово видаляються в middleware, після чого підставляються перевірені клейми з токена.
- Заголовок `X-Correlation-Id` генерується/прокидається в усі downstream-запити.

## Наслідки
- Екран завантажується за мінімальний час (тривалість найповільнішого з двох паралельних запитів).
- Забезпечено graceful degradation при частковій відмові вторинного сервісу.
