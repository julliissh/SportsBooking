# ADR-0002. Шлюз Ocelot перед монолітом

## Статус

Accepted (2026-09-10)

## Контекст

Зараз клієнт звертається напряму до моноліту на порту `5100`. У рамках поетапної міграції (патерн Strangler Fig) моноліт буде розбито на незалежні мікросервіси. Клієнт не повинен знати про внутрішню структуру системи та адреси окремих сервісів.

## Розглянуті варіанти

1. **Без шлюзу.** Клієнт напряму звертається до моноліту, а потім до кожного нового сервісу. Будь-яка зміна адрес або винесення сервісу ламає клієнтську частину.
2. **Ocelot.** Легкий шлюз для ASP.NET Core. Маршрути, агрегація та політики налаштовуються декларативно у файлі `ocelot.json`.
3. **YARP (Yet Another Reverse Proxy).** Гнучкий зворотний проксі від Microsoft. Дуже швидкий, але потребує більше програмного коду для налаштування маршрутизації та політик.
4. **Хмарний шлюз (Azure API Management / AWS API Gateway).** Потужні керовані рішення, але вимагають прив'язки до хмарного провайдера та додаткових витрат/налаштувань для локальної розробки.

## Рішення

Обрано **Ocelot**. Він ідеально підходить для навчального проєкту та реалізації патерну Strangler Fig:
- Маршрути описуються декларативно у JSON-файлі без потреби писати окремий код маршрутизатора;
- Шлюз працює на окремому порті `5000` і спочатку перенаправляє весь трафік `/api/*` на моноліт (`localhost:5100`);
- Надалі міграція на окремі мікросервіси зводиться до оновлення адрес у конфігурації без змін у клієнтському коді.

## Наслідки

### Плюси:

- Єдина точка входу для всіх клієнтів: `http://localhost:5000`;
- Приховування внутрішньої структури та портів сервісів від зовнішнього світу;
- Можливість централізовано реалізувати наскрізну функціональність (CORS, логування, генерація `X-Correlation-Id`, обмеження частоти запитів);
- Зміна маршрутів виконується через конфігурацію, без перекомпіляції клієнта.

### Мінуси:

- З'являється додатковий компонент (процес), який потрібно запускати, підтримувати та моніторити;
- Шлюз стає потенційною єдиною точкою відмови (Single Point of Failure);
- Додатковий мережевий стрибок додає невелику затримку (+2–5 мс) до кожного запиту.
